# Control and coverage decisions

Use this table when similar signals, divergent timing or multiple actors make a control choice ambiguous. Concrete source-index examples are in the [San d'Oria authoring record](../../../../timelines/sandoria-authoring.md); its encounter IDs and timings are not general rules.

| Situation                                 | Decision and check                                                                                                                                                                                                                                                                                                                                     |
| ----------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Several IDs share a cue and continuation  | Use one display and accept the observed ID set. Verify each ID against the same display. R12S Double Sobat is an example.                                                                                                                                                                                                                              |
| Player response or subsequent cues differ | Use separate paths when a signal distinguishes them. Keep shared cues outside the branch until the selector arrives. R12S Netherwrath Near and Far differ even though the timing agrees.                                                                                                                                                               |
| A known route drifts                      | Sync to an observed event and verify a forecast made before the next major impact.                                                                                                                                                                                                                                                                     |
| The first selector is missing             | Use `when resume-at` when the same option can resume at a known offset. Use a fallback option when the observed recovery signal requires its own timing or remaining schedule. Compare original and signal-removal replay.                                                                                                                             |
| Checkpoint can start independently        | Check independent entry, cancellation of the preceding schedule, and restart after a wipe. Use a phase-scoped completion signal when it is observed and specific to that boundary.                                                                                                                                                                     |
| Same ability on different routes          | Find an earlier distinctive source or neighboring signal. A later shared ability is not automatically a selector. Replay subsequent shared signals to check conflicting selections.                                                                                                                                                                    |
| Choice visible only shortly before impact | Measure selection-to-impact time. Set an achievable lead for that first conditional event, record why, and keep longer warning goals for later events.                                                                                                                                                                                                 |
| Opening ability reused later              | Check whether another phase would make the old entry signal restart the schedule. Keep one phase when event syncs suffice, or constrain transitions with observed context.                                                                                                                                                                             |
| Merge near a scheduled display            | Test control just before, at and after the display, including raw milliseconds that round to the same tenth. The merge may cancel option events. An earlier cast start can replace the schedule before impact while the option supplies the initial warning.                                                                                           |
| Several bosses casting concurrently       | Keep simultaneous displays distinct. Check whether a sync shifts another boss's schedule. If the joint schedule ends at a death, identify the actual runtime signal and state whether the survivor's tail is authored.                                                                                                                                 |
| Earlier progression                       | Widening an Ability window can repair execution too late for advance warning. Check whether a sufficiently long StartsUsing signal can restore the schedule before the query cutoff.                                                                                                                                                                   |
| Repeated block                            | Separate a complete observed body, an actual next boundary, and a synthetic future iteration. Use `count` when the encounter establishes a fixed cap. Test the last complete body, suppression of the next iteration, and any earlier `until`. If the exit starts a fresh schedule, use a phase transition and check cancellation of the old schedule. |

For R12S Raptor and Serpentine, impact identifies a known offset in the selected path. For San d’Oria Kirin, the ADCD and Double Cast recovery schedules have separate signal anchors and lead-time evidence. Preserve that distinction until a shared offset is verified.

### Choosing a signal-relative schedule

The [sequence syntax](timeline-schema.md#신호로-시작하는-sequence--구현-예정) is parsed and validated. Execution is pending. Use the current KDL schema for executable timelines. When reviewing a candidate for migration, check what each signal should start, move, or cancel.

| Observation                                                                       | Structure                                                                                                |
| --------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| A cast starts a short schedule while the current encounter stage stays active     | Consider a sequence. San d’Oria’s survivor casts are the first migration case.                           |
| A helper effect is already predictable before its parent mechanic signal          | Keep the existing schedule or loop and verify the available lead. Malphas’s Puppet waves are an example. |
| A boundary cancels the previous schedule and anchors a continuation or checkpoint | Use a phase transition. Queen Eternal and Lindwurm supply examples.                                      |
| The next route depends on earlier choices                                         | Retain the selection history and merge rules. Varis’s Gunshield order is an example.                     |

### Moving from a waiting loop to a follow-up phase

1. Use `until` if the signal should stop only the loop and preserve the phase’s other reservations. Use `enter from` if it should cancel the old schedule and anchor a new one. Check which pending displays must survive before moving them.
2. Anchor the follow-up phase to the first reliable transition signal. Set its window on the preceding phase clock and add a later sync when the logs support it. If a return packet reuses the opening ID, guard the opening entry so it cannot restart the waiting phase while the follow-up is active.
3. When rewriting an existing timeline, replay the same inputs before and after. Compare display IDs and timestamps, then query the first follow-up forecast before impact. Check transition before the loop starts and after several iterations, delayed follow-up sync, and return without restart. Record any timing deltas and label synthetic cases separately.

In [Queen Eternal](../../../../timelines/queen-eternal-hold-authoring.md), `8EFF` StartsUsing moves `hold` to `castellation`. The matching Ability corrects the follow-up clock. The return `8F00` syncs the follow-up without reopening `hold`.

### Verifying a complete loop body

1. Before writing nested branches, mark the start signal and the next observed start in multiple long logs. List the intervening major casts by source, ID, and relative time. Include the shared lead-in that repeats before a branch choice.
2. Compare the body with phase-owned displays. Inspect `review.coverage.loops[].first_outside_body_candidate` and its raw indices. Keep a display outside the loop when its independent timing or cancellation is supported by the logs.
3. Interrupt a replay mid-cycle with an applicable transition or wipe. Verify that pending displays owned by that body disappear. For a counted loop, also replay across the final boundary and check the next shared cue and the absence of an extra iteration.

### Splitting a long segment into phases

| Observation                                                                    | Authoring decision                                                                                                      |
| ------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------- |
| A reliable signal ends the prior schedule and anchors a distinct continuation  | Create a phase with `enter from`. Move the continuation’s displays and syncs to the new clock.                          |
| A mechanic starts a new section in a guide, but prior reservations still apply | Keep the same phase. Use a sync for drift or a branch for alternate paths.                                              |
| The pull can begin at a checkpoint                                             | Keep its independent entry on the checkpoint opening phase. Require the preceding phase for later internal transitions. |

Before splitting, record the boundary signal, predecessor, and first major cue in multiple long logs. Replay early and late transitions, a missing boundary signal, and any opening ID reused later. Verify which reservations cancel, whether the first follow-up cue still has enough lead, and whether checkpoint and wipe behavior survives. Recheck each `from` guard and evaluation binding against the new phase owners.

In [R12S](../../../../timelines/r12s-authoring.md), consider the transition into the first Slaughtershed cycle in the first half and into the Cosmic Kiss sequence in the second half. These are candidates for evidence review. Splitting the first half changes which phase is active at `B539`; check the completion guard for every reachable clear path. Keep independent checkpoint entry at the start of the second half and verify restart from there.

For each consequential decision, preserve the source indices, competing interpretation, chosen control and user-visible effect. Scope changes and relaxed lead targets are model revisions: record them before fresh independent evaluation.

A compact coverage table should identify each choice/loop, development observations, held-out observations and synthetic checks. Use `review.coverage` for signal selections, bounded display bodies, and first body gaps; preserve its role and unmatched-display warnings. Check `body_coverage_inputs` before interpreting zero counts from an older report. A terminal body without the next observed anchor remains unverified; combine separate test evidence explicitly. An unobserved held-out route stays unverified even when every held-out file passes. See the [evaluation contract](authored-evaluation.md#분기반복-커버리지) for each metric's limits.
