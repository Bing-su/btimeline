# 타임라인 KDL 스키마 초안

상태: **설계 초안, 구조 검사와 기본 재생의 첫 구현**. 이 문서는 사람이 편집하고 외부 실행기가 사용할 최종 타임라인의 계약이다. `mine`이 만드는 `process 1`은 관측 그래프이며 `timeline 1`과 다르다. 현재 구현 범위와 미검사 항목은 [오프라인 재생 안내](OFFLINE_REPLAY.md)에 정리한다. 생성·검증 구현과 실제 로그 비교 결과에 따라 초안을 변경할 수 있다.

FFLogs JSON과 mode에서 lifecycle·공통 시전 일정·동기화를 만드는 경로는 [생성 계약](GENERATION.md)에 정의한다. 최종 KDL 문법은 이 문서를 따르며 생성 근거는 실행 입력으로 요구하지 않는다.

실제 전투에 연결하는 실시간 타임라인 실행기는 이 저장소에서 구현하지 않는다. 대신 KDL과 기록된 신호로 실행 의미를 확인하는 오프라인 재생기를 구현한다. 최종 KDL에는 실행에 필요한 시각, 신호, window, 전환, 분기, 반복과 초기화 규칙을 모두 담아, 외부 실행기가 별도 evidence 없이 KDL 하나로 동작할 수 있도록 설계한다. evidence는 생성 근거와 검토를 위한 선택적 자료이며 실행 조건으로 참조하지 않는다. 영어를 기준으로 작성하고, 다른 언어의 번역은 앞서 정한 대로 별도 제공한다.

cactbot의 실제 신호와 전투 자료는 참고하지만 cactbot 파일과의 호환은 목표가 아니다. 최소한 cactbot이 사용하는 로그 타입과 필드를 표현할 수 있어야 한다. 이전 v2 계약과도 호환되지 않는다. 관련 조사: [생명주기](CACTBOT_LIFECYCLE_RESEARCH.md), [일반 토벌전 반복](CACTBOT_NORMAL_TRIAL_LOOPS.md).

시계 설계의 근거는 [분기·합류·탈출 후 동기화 조사](CACTBOT_CLOCK_RESEARCH.md)에 정리한다. 후속 sync는 유지하되 option·merge·on-exit의 독립 시계 보정은 두지 않고, 가장 가까운 phase 또는 반복 회차의 시간축을 공유한다.

## 기본 규칙

| 항목   | 계약                                                                                                                                                                                       |
| ------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 문서   | KDL 2 문서에 `timeline 1 "이름" { ... }` 루트 하나. `1`은 스키마 버전이다.                                                                                                                 |
| 이름   | 표시 이름과 NPC 매칭 이름은 영어를 기준으로 한다. `locale`은 두지 않으며 번역은 별도 리소스로 제공한다.                                                                                    |
| 시간   | 음이 아닌 유한한 초, 0.1초 단위. 정수 입력도 허용하지만 출력은 `0.0`, `42.0`, `42.5`처럼 소수 첫째 자리까지 표시한다. `42.55` 같은 직접 입력은 오류다. 내부 계산은 정수 0.1초 단위를 쓴다. |
| 식별자 | `phase`, `branch`, `event`, `loop` ID는 각 종류 안에서 문서 전체에 고유하다. `option` ID는 소속 branch 안에서 고유하다. 참조는 정확히 하나로 해석돼야 한다.                                |
| 검토   | 사람의 확인 상태는 별도 evidence에 둔다. 자동 생성만으로 확정하지 않는다.                                                                                                                  |
| 검증   | 알 수 없는 속성·자식, 중복 필드, 잘못된 타입, 모호한 참조, 지원하지 않는 버전은 오류다. 조건을 조용히 버리지 않는다.                                                                       |

원본 관측과 evidence는 밀리초를 보존한다. 관측에서 후보 시각을 만들 때 가까운 0.1초로 반올림하고 정확히 중간이면 큰 값으로 정한다. `42.549`초는 `42.5`초, `42.550`초는 `42.6`초다. 원본 값과 차이를 기록하고 반올림으로 순서·동시성·window·충돌이 달라지는지 재검증한다.

window와 시계 비교에도 해당 시계의 기준점으로부터 계산한 관측 상대 시각을 같은 규칙으로 반올림해 사용한다. 따라서 경계 일치는 반올림된 값으로 판단한다. 별개의 관측은 원본 시각 순으로 처리하고 원본 시각도 같으면 원본 기록 순서를 유지한다. 반올림한 시각이 같다는 이유로 관측을 하나로 합치거나 순서를 바꾸지 않는다. 하나의 관측에 여러 조건이 일치할 때는 아래 충돌 규칙을 적용한다.

## 스키마의 공통 실행 규칙

이 규칙은 KDL을 사용하는 실시간 실행기와 오프라인 재생기에 공통으로 적용한다. 문법별 세부 조건은 아래 각 절에서 정의한다.

| 상황                           | 동작                                                                                                                                                                                                                                                |
| ------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 같은 시각의 신호와 예정 이벤트 | 신호의 유효성을 판단하고 제어 전환과 sync를 적용한 후, 여전히 활성 상태이며 그 시각에 예정된 이벤트를 처리한다. 전환으로 닫힌 구간의 이벤트는 취소한다.                                                                                             |
| 경쟁하는 동작                  | 하나의 관측이 서로 배타적인 동작에 일치하면 `ambiguous`로 보고하고 임의 선택하지 않는다. 동일한 동작은 한 번만 적용한다. 같은 0.1초에 속한 별개 관측을 자동으로 충돌시키지 않는다. lifecycle의 우선순위와 phase 전환은 아래 수명주기 규칙을 따른다. |
| 시계를 앞으로 보정             | 보정 전후 시각 사이에서 미처리된 이벤트는 건너뛰고 기록한다. 보정된 시각에 예정된 활성 이벤트는 처리한다.                                                                                                                                           |
| 시계를 뒤로 보정               | 이미 처리한 이벤트와 회차를 다시 실행하지 않는다. 반복 시계는 아래 반복 규칙에 따라 보정한다.                                                                                                                                                       |
| 구간 시작 신호                 | phase 진입은 새 phase 시계를, option 선택은 상대 기준점을 0.0으로 시작한다. 새 구간의 0.0 이벤트는 위 순서에 따라 처리한다. 같은 관측을 이벤트 sync로 다시 적용하지 않는다.                                                                         |
| branch 선택 종료               | 시간 경과나 보정으로 close에 도달하거나 지나면 선택을 닫고 미선택이면 unresolved를 기록한다. 뒤로 보정해도 선택을 다시 열지 않는다. 이미 선택한 option의 일정과 merge의 감시는 각각의 종료 조건까지 유지한다.                                       |
| 유휴 상태                      | start 전에는 enter만으로 phase에 진입하지 않는다. 같은 관측으로 start와 첫 enter가 성립하면 진입한다.                                                                                                                                               |

option·merge·on-exit 신호의 원본 시각이 반올림한 기준점보다 앞서더라도, 새 구간의 0.0 이벤트는 같은 원본 시각의 모든 신호 처리 후 실행한다. 예를 들어 1.051초에 선택하면 기준점은 1.1초이지만 0.0 이벤트는 1.051초에 실행하고 1.0 이벤트는 2.1초에 예정한다. 같은 원본 시각의 후속 sync로 해당 구간이 이동하거나 닫히면 그 보정·전환을 먼저 반영한다.

아직 시작하지 않은 반복의 시작점을 phase 시계의 전진 보정이 지나치면, 보정된 phase 시각에 해당하는 회차부터 시작한다. 지나친 완전한 회차의 직접 이벤트와 현재 회차에서 보정 시각보다 앞선 직접 이벤트는 `skipped`로 기록하고, 보정 시각의 이벤트는 신호 처리 뒤 실행한다. 지나친 회차의 각 branch는 선택을 추정하지 않고 `unresolved`로 기록하며 해당 선택 이력을 미해결로 갱신한다. 현재 회차는 보정된 위치에 따라 branch를 열거나 미해결로 닫는다. 보정이 여러 반복의 시작점을 지나치면 시작 시각, 같은 시각이면 문서 순서대로 본문 시작 여부를 판단하며 동시 본문 위반은 보정 시각에 기록한다. 지나친 회차는 뒤로 보정해도 재실행하지 않는다. 수명주기 규칙에 없는 여러 제어 동작의 조합은 별도 재생 사례로 확정하며 실행기별 재량으로 간주하지 않는다.

## 타임라인 작성·검증 제약

아래 조건을 만족하지 않는 문서는 검증 오류다. 조건을 충족해도 실제 게임과 일치하는지는 별도로 검토한다.

| 대상           | 작성 제약                                                                                                                                                                                                                                                                                                                    |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 문서와 ID      | 지원하는 버전과 알려진 필드만 사용하고, 위의 타입·ID 고유성 및 참조 규칙을 지킨다.                                                                                                                                                                                                                                           |
| 시간과 window  | 시간은 0.1초 단위이며 각 구간의 범위와 window 조건을 지킨다.                                                                                                                                                                                                                                                                 |
| 구조와 중첩    | branch는 phase 또는 loop의 직접 자식으로만 둔다. loop는 phase 또는 option의 직접 자식으로 둘 수 있지만, 모든 조상에 다른 loop가 없어야 한다. `loop → branch → option → loop`도 오류다.                                                                                                                                       |
| 합류·탈출 본문 | merge와 on-exit의 실행 본문에는 event만 둔다. merge의 when과 신호 조건, event의 sync는 허용한다. branch·loop·phase를 이 본문에 중첩하지 않는다.                                                                                                                                                                              |
| 선택과 합류    | branch마다 둘 이상의 option과 각 option의 선택 신호를 둔다. `merge`에는 하나 이상의 공통 신호 조건을 지정한다. 해당 신호의 실제 발생 여부는 로그 비교·사람의 검토로 확인한다.                                                                                                                                                |
| 선행 선택      | requires의 참조 대상 존재 여부·자기 참조·순환 참조와 한 option이 같은 branch의 서로 다른 선택을 동시에 요구하는 모순은 정적으로 검사한다. 선행 실행 결과의 존재는 재생 시 검사하며 모든 경로의 선후관계 증명을 요구하지 않는다. 문서 배치 순서로 선후를 결정하지 않고, 미래 선택 대기·신호 보관·소급 선택은 허용하지 않는다. |
| 보정 범위      | 같은 phase 또는 반복 회차를 공유하는 이벤트와 window는 함께 보정되어도 되는 진행으로 작성한다. 서로 독립적으로 지연되는 병렬 진행을 별개의 option 시계처럼 취급하지 않는다. 표현할 수 없는 병렬 진행은 제한으로 기록한다.                                                                                                    |
| 신호 충돌      | 같은 branch에서 선행 선택 조건이 동일한 두 option의 리터럴 신호가 겹치면 해당 선행 선택의 도달 가능성 증명 없이 작성 오류로 보고한다. 그 밖에도 when·requires·활성 구간을 함께 고려해 조건이 동시에 성립함을 정적으로 증명할 수 있으면 오류로 보고한다. 정적으로 판단하지 못한 충돌은 재생 시 `ambiguous`로 보고한다.        |

다음 두 제약도 작성 원칙으로 적용한다. 정적 검증은 명확한 구조·범위 위반을 검사하고, 관측에 따라 결정되는 조건은 재생에서 확인한다. 모든 가능한 실행 경로의 증명을 요구하지 않는다.

| 대상         | 작성 원칙과 확인 방법                                                                                                                                                                                                                                                                                                                  |
| ------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 동시 반복    | 같은 phase에서 본문을 실행 중인 loop는 최대 하나다. 시작 전 탈출 감시만 하는 loop는 세지 않는다. 서로 배타적인 option의 반복과 앞 반복이 탈출한 뒤 시작하는 반복은 허용한다. 명확한 겹침은 정적 오류다. 재생 중 두 번째 loop 본문을 시작하려 하면 시작하지 않고 작성 제약 위반을 보고하며, 임의로 직렬화하지 않는다.                   |
| 회차 안 완료 | 반복 안 option·merge의 이벤트와 sync 중심 시각은 가장 늦게 선택·합류할 수 있는 시점까지 고려해 회차 끝보다 앞에 둔다. 반복 안 merge의 모든 when에는 유한한 at·before·after window가 필요하다. 명확한 범위 초과는 정적 오류이며, 보정 등 관측에 의존하는 범위 위반은 재생에서 검사한다. window의 허용 오차는 회차 활성 범위에 제한한다. |

예를 들어 every=20.0에서 합류 window의 끝이 18.0이면 그 뒤 3.0초의 이벤트는 회차 밖이므로 오류다. 회차 끝과 정확히 같은 시각도 허용하지 않는다. option 선택 window는 [open, close)이므로 0.1초 단위의 가장 늦은 선택 시각은 close - 0.1이다. 이 범위 검사에 모든 가능한 로그나 보정의 증명을 요구하지 않는다.

검증 결과는 구조·범위 오류, 특정 재생에서 발견한 위반, 아직 검사하지 못한 조건을 구분한다. 정적 검사나 일부 로그 재생의 통과를 모든 실행 경로의 보장으로 표시하지 않는다. 비교 상태인 unresolved와도 구분해 검사 범위와 미검사 조건을 명시한다.

window끼리 겹친다는 사실만으로 오류로 판정하지 않는다. 능력 ID·선행 선택 등 전체 조건으로 유일하게 구별할 수 있으면 넓은 window도 허용한다. 새 제약으로 실제 전투를 표현하지 못하면 아래 원칙에 따라 스키마의 한계로 기록한다.

생성·검토 시 관측되지 않은 신호나 경로를 추측해 확정하지 않는다. 근거 부족과 표현 불가는 evidence 및 검증 결과에 남기되, evidence가 없다는 이유만으로 KDL을 문법 오류로 판정하지 않는다. 작성 제약을 만족시키려고 실제로 존재하지 않는 신호를 만들지 않는다. 실제 전투를 현재 문법으로 표현할 수 없다면 제한을 기록하고 사례를 검토해 스키마 변경 여부를 결정한다.

## 사람이 읽는 이벤트 ID

모든 `event`의 첫 인자는 읽고 검색할 수 있는 고유 ID이며 표시 `name`과 별개다.

```kdl
event "crown-opening" 11.2 name="Crown of Arcadia"
event "crown-after-comets" 72.4 name="Crown of Arcadia"
```

생성기는 이름이나 역할을 바탕으로 읽을 수 있는 ID를 제안하고 사람이 수정할 수 있게 한다. 같은 이름의 별개 이벤트는 역할로 구별하고 정보가 부족하면 `crown-01`처럼 접미사를 붙인다. 해시나 임의 숫자만을 기본 ID로 삼지 않는다. 표시 이름·시간·번역·문서 순서 변경이나 다른 이벤트의 추가·삭제 때문에 기존 ID를 바꾸거나 재번호를 매기지 않는다. 기존 문서를 바탕으로 재생성할 때 대응이 모호하면 이름이나 시간만으로 임의 재사용하지 않고 검토 대상으로 남긴다. 별도 초기 생성 결과의 ID가 입력 변경 이후에도 같다고 보장하지 않는다.

반복 안 이벤트는 한 ID를 유지하며 각 실행은 ID와 반복 회차를 함께 기록한다. 원본 관측·검토 결과에서도 정의 ID와 회차를 구분한다.

## 전체 예시

ID·시간·신호는 문법 설명용 가상 예시다. 특정 콘텐츠의 실제 전투 정의가 아니다.

```kdl
timeline 1 "Example" {
    start "InCombat" inGameCombat="1"
    wipe "ActorControl" command="4000000F"

    phase "opening" {
        enter "InCombat" inGameCombat="1"
        event "crown" 11.2 name="Crown of Arcadia" {
            sync 6.1 "StartsUsing" id="B406" source="The Tyrant" before=1.0 after=1.0
            sync 11.2 "Ability" id="B406" source="The Tyrant" before=1.0 after=1.0
        }

        branch "weapon" open=20.0 close=35.0 {
            option "sword" {
                when "Ability" id="A001"
                event "sword-hit" 5.0 name="Sword attack"
            }
            option "staff" {
                when "Ability" id="A002"
                event "staff-hit" 5.0 name="Staff attack"
            }
            merge {
                when "Ability" id="A003"
                event "shared" 3.0 name="Shared attack"
            }
        }
    }

    phase "second" {
        enter "StartsUsing" id="C123" source="The Tyrant" from="opening" at=100.0 before=20.0 after=20.0
        event "second-opening" 7.0 name="Second phase attack"
    }
}
```

`crown`과 두 `sync`의 시각은 opening 진입 기준이다. `sword-hit`은 선택 신호 기준 5.0초이고, `shared`는 공통 합류 신호 기준 3.0초다. `second`는 opening 시계 80.0~120.0초에 `C123`을 관측했을 때 진입한다. 예시의 wipe 신호를 모든 콘텐츠의 전멸 신호로 일반화하지 않는다.

## 시계와 구간

재생 순서는 원본 관측의 공통 시간축을 사용한다. 아래 예정 시계의 보정은 원본 관측 시각이나 이미 처리한 관측의 순서를 바꾸지 않는다. 시간 window는 해당 구간에서 계산한 상대 시간을 0.1초로 반올림해 비교한다.

| 기준           | 의미                                                                                                     |
| -------------- | -------------------------------------------------------------------------------------------------------- |
| 전투 시계      | `start`에서 0.0으로 시작하며 루트 이벤트의 예정 시각에 사용한다. phase 전환과 보스 처치 뒤에도 유지된다. |
| phase 시계     | phase 진입에서 0.0으로 시작하며 해당 phase의 진행과 window를 보정한다.                                   |
| 반복 회차 시계 | 회차 시작에서 0.0으로 시작하며 반복 본문을 보정한다. 다음 회차도 보정된 시작점에서 예정한다.             |

`event "id" 시간 name="이름"`과 그 아래 `sync` 시각은 가장 가까운 구간의 시작 기준이다. option 선택·merge 합류·on-exit 탈출은 독립 시계를 만들지 않고 **가장 가까운 phase 또는 반복 회차의 시각을 시작 기준점으로 기록**한다. 기준점은 그 실행 동안 고정되며, 그 아래 상대 시각을 더해 공유 시간축의 목적 시각을 계산한다. 루트 이벤트의 sync는 전투 시계를 보정한다.

예를 들어 phase 시각 20.0에 option을 선택하고 그 안에 `sync 5.0`이 있으면 목적 시각은 phase 25.0이다. 신호를 phase 27.0에 관측하면 phase 시계를 25.0으로 보정한다. 같은 phase에 직접 작성한 후속 이벤트와 window도 함께 이동한다. 선택 후 경과 시간만 따로 보정하지 않는다. 반복 안의 option도 같은 방식으로 회차 시간축을 공유한다.

반복 본문의 sync는 부모 phase·option의 시간축을 보정하지 않는다. 부모 보정은 아직 시작하지 않은 반복의 시작 시각에 반영하며, 이미 시작한 반복 회차의 기준점을 소급 변경하지 않는다. 이미 실행한 이벤트는 다시 실행하지 않는다. 독립 시계 선택 속성이나 보정 대상 지정 속성은 두지 않는다.

## 신호와 window

흔한 신호는 한 줄로 쓴다. `start`, `wipe`, `boss-complete`, `finish`, `zone-exit`, `enter`, `when`, `until`, `sync`는 해당 위치에서 신호의 역할을 나타낸다. 이 중 `sync`만 시간 다음에 로그 타입을 쓴다.

```kdl
start "InCombat" inGameCombat="1"
enter "StartsUsing" id="C123" source="The Tyrant"
sync 11.2 "Ability" id="B406" source="The Tyrant" before=1.0 after=1.0
```

로그 타입에 정의된 필드는 문자열 속성으로 쓴다. 한 줄의 여러 필드는 AND이며 리터럴은 필드 전체와 일치한다. `id`는 해당 로그 타입의 필드이고 이벤트 ID는 `event`의 첫 인자다. 필드값은 문자열로 보존하므로 능력, 효과, 테더, 마커의 ID를 같은 종류로 가정하지 않는다. 같은 이름의 NPC가 여러 개일 때 이름만으로 개체를 구별했다고 간주하지 않는다.

대안이나 정규식이 필요할 때만 블록을 사용한다.

```kdl
sync 42.0 "Ability" source="The Tyrant" {
    field "id" "B430" "B431"
    regex "target" "^Player .*$"
}
```

`field`의 값은 하나 이상이며 같은 필드 값끼리 OR다. `regex`의 패턴도 하나 이상의 OR다. 같은 필드를 속성·`field`·`regex` 중 하나로 한 번만 지정하고 필드 간에는 AND다. 역할을 나타내는 `at`, `before`, `after`, `from` 등 예약 속성과 이름이 충돌하는 로그 필드는 `field "필드명" "값"`으로 표현한다. 정규식은 regress의 ECMAScript 문법, 기본 플래그(대소문자 구분, multiline 비활성)로 필드 전체에 일치시킨다. 패턴은 슬래시 구분자 없이 작성하고 지원하지 않는 문법은 오류다. 반복 구조의 필드 문법과 로그 타입·필드 목록은 별도 확정한다.

다른 신호 타입이 OR인 경우 같은 역할의 노드를 여러 줄 둔다. 예: `start "InCombat" ...`과 `start "SystemLogMessage" ...`은 둘 중 하나가 전투를 시작한다. 각 신호 노드에 window를 둘 수 있으면 그 window를 개별적으로 평가한다. 일치하는 대안이 둘 이상이어도 결과 동작과 목적 시각이 같으면 한 번만 적용하고, 서로 다른 동작이나 목적 시각에 일치하면 `ambiguous`로 보고해 추측하지 않는다. 특히 여러 `sync`는 같은 이벤트에 속하더라도 각자 시각과 window가 있다.

생성기가 출력하는 모든 시간 window는 기본값도 포함해 명시한다. 사람이 직접 작성할 때 `sync`는 `before`·`after`를 둘 다 생략하면 각각 2.5초다. 하나만 지정하면 오류다. window는 양 끝을 포함하며 보정 전 해당 시계에 적용한다. 서로 다른 활성 동기화 목적지가 같은 관측과 일치하면 `ambiguous`를 보고하고 시계를 바꾸지 않는다.

## 전투 수명주기와 페이즈

루트의 `start`, `wipe`, `boss-complete`, `finish`, `zone-exit`은 각각 신호를 지정한다. 생략한 사건을 시간 경과나 다른 사건에서 추측하지 않는다. 같은 역할 노드를 여러 개 두면 OR다.

| 사건                  | 동작                                                                                               |
| --------------------- | -------------------------------------------------------------------------------------------------- |
| `start`               | 유휴 상태에서 전투 시계를 0.0으로 시작하고 첫 phase 진입을 기다린다. 실행 중 반복 신호는 무시한다. |
| `wipe`                | 모든 시계·선택·예약 이벤트를 초기화하고 다음 `start`를 기다린다.                                   |
| `boss-complete`       | 현재 phase와 예약 이벤트를 닫고 다음 phase 진입을 기다린다. 전투 시계와 선택 이력은 유지한다.      |
| `finish`, `zone-exit` | 모든 상태를 초기화하고 유휴 상태로 돌아간다.                                                       |

`phase`에는 하나 이상의 `enter` 신호가 필요하며 이는 OR다. 전투가 시작된 상태에서만 진입할 수 있고 유휴 상태에서는 enter를 무시한다. 같은 관측의 start로 전투가 시작되는 경우는 허용한다. 진입 시 해당 phase 시계를 0.0으로 시작하고 기존 phase를 닫는다. 활성 phase의 동일 진입 신호는 다시 시작하지 않는다. 같은 관측이 유효한 여러 phase 진입 조건에 일치하면 어느 쪽도 선택하지 않고 `ambiguous`로 보고한다.

필요하면 `enter`에 `from="phase-id"`와 `at`, `before`, `after`를 지정한다. `from`은 현재 활성 phase에 대한 조건이며, window는 **그 phase의 상대 시계**를 사용한다. `at`이 있으면 `from`이 필수이고 window 생략 기본값은 `sync`와 같다. `from`만 지정할 수도 있다. `from`이 없으면 특정 이전 phase에 제한하지 않는다. 최초 진입이나 `boss-complete` 후 대기 중인 진입에는 활성 `from`이 없으므로 해당 제약 없는 신호가 필요하다.

이전 선택에 따라 다음 선택의 시간 창이 달라지면 기믹 구간을 phase로 표현하고, 같은 대상 phase에 이전 구간별 `enter from`을 둘 수 있다. [Varis EX의 P3 발췌](../tests/fixtures/timeline/varis-choice-windows.kdl)는 Loaded 진입을 이전 Reinforced 시계의 52.8초 또는 Electrified 시계의 58.7초에 받는 예시다. [검증 범위](VARIS_ANTIVIRUS_VALIDATION.md)의 여섯 순서·창 경계 확인은 생성기의 선택 이력 학습 완료와 구분한다.

타임라인은 유휴 상태로 시작한다. 같은 신호가 `start`와 첫 phase `enter`에 일치하면 두 시계를 같은 관측 시각에 시작한다. 여러 lifecycle 사건에 일치하면 `zone-exit`, `wipe`, `finish`, `boss-complete`, `start` 순으로 하나만 적용한다. `zone-exit`, `wipe`, `finish`는 같은 관측에서 새 phase나 option을 시작하지 않는다.

같은 관측이 `boss-complete`와 다음 phase의 `enter`에 일치하면 이전 phase를 닫고 다음 phase로 진입하는 하나의 전환으로 처리한다. `from`과 window는 이전 phase를 닫기 전 상태를 기준으로 평가한다. 같은 관측이 현재 loop의 `until`과 새 phase의 `enter`에 일치할 때도 phase 전환을 한 번 적용한다. 이때 이전 phase가 닫히므로 해당 loop의 `on-exit`은 실행하지 않는다. 유효한 새 phase가 둘 이상이면 `ambiguous`로 보고하고 어느 phase로도 전환하지 않는다. lifecycle·전환·선택과 이벤트 sync가 충돌하면 제어 동작을 우선하고 그 관측을 이벤트 sync로 재사용하지 않는다. FFLogs fight 경계를 ACT의 실제 시작·전멸 신호로 간주하지 않는다.

## 이벤트와 동기화

`event "id" 시각 name="이름"`은 가장 가까운 구간의 시작 기준으로 작성한 표시 예정 시각이다. option·merge·on-exit에서는 앞서 정의한 기준점을 더해 공유 시계로 계산한다. `duration=초`는 선택적 표시 지속시간이며 시전 시간과 다르다. `visible=#false`는 해당 이벤트만 숨긴다. 생략 시 `#true`다.

이벤트에 `sync 시각 "타입" 필드...`를 여러 개 두어 시전 시작과 발동처럼 서로 다른 시점의 신호를 표현한다. 각 sync는 독립적인 window를 가지며, 유일하게 일치하면 위의 기준점 계산에 따라 가장 가까운 phase 또는 반복 회차의 시계를 보정한다. 루트에서는 전투 시계를 보정한다. 같은 시각·같은 동작을 갖는 여러 타입은 각각 `sync`로 작성하고 하나의 관측을 한 번만 처리한다. 같은 시각 이벤트의 표시는 문서 순서를 따르되 이를 인과관계로 취급하지 않는다.

신호 하나를 이벤트에 붙이는 것이 불편한 단순 행에만 단축 속성을 추가하는 설계는 아직 도입하지 않는다. 이벤트 ID와 로그 필드의 이름 충돌을 피하고, 모든 동기화에 동일한 `sync` 문법을 쓴다.

## 브랜치와 합류

`branch "id" open=초 close=초`는 소속 phase 또는 loop 회차의 `[open, close)`에서 선택 신호를 받는다. `open < close`이며 해당 구간의 시계 기준이다. 선택지는 둘 이상이다. 각 `option` 안에 `when "타입" 필드...`를 하나 이상 두며 여러 신호는 OR다. 조건이 없는 option은 오류다.

`option "id" fallback=#true`는 같은 branch의 선택이 비어 있을 때만 신호를 검사한다. 예를 들어 첫 선택 신호를 놓쳤을 때 후속 시전으로 남은 일정을 시작할 수 있다. 미선택 상태에서 둘 이상의 선택지가 동시에 일치하면 기존 충돌 규칙을 적용한다. 복구 일정의 기준은 실제로 선택한 후속 신호 시각이다.

선택된 option만 활성화되고 선택 신호를 상대 시각 0.0의 기준점으로 기록한다. 신호가 오지 않으면 다른 option을 추정하지 않는다. 서로 다른 option이 같은 관측에 일치하거나 필요한 선행 선택이 없으면 선택을 확정하지 않고 `ambiguous` 또는 `unresolved`로 보고한다. window가 닫혀도 선택되지 않으면 `unresolved`다. 선택이 확정된 뒤 모순되는 선택 신호가 오면 상태를 바꾸지 않고 충돌을 보고한다.

각 option 안에 `requires "branch-id" "option-id"`를 0개 이상 둘 수 있다. 조건들은 AND다. 존재하지 않는 branch·option 참조, 자기 branch 참조와 순환 참조는 정적 오류다. 선행 실행 여부는 문서 배치 순서로 추정하지 않고 재생 시 확인한다. **선택 이력은 phase 전환과 `boss-complete`를 넘어 전투가 끝나거나 wipe될 때까지 유지**하므로 이전 phase의 선택을 참조할 수 있다. 같은 branch가 phase 재진입이나 반복 회차에서 다시 실행되면 선택 상태는 새로 시작하고 이전 실행의 이력은 보존한다. requires는 해당 관측 전에 가장 최근에 실행된 참조 branch의 선택을 본다. 그 실행이 미해결이거나 아직 없으면 해당 관측으로 선택하지 않고 unresolved로 보고한다. 더 오래된 확정 선택으로 대신하지 않으며, 다른 option이 선택됐으면 조건이 거짓이다. 미래 선택을 기다리거나 관측을 저장해 나중에 소급 적용하지 않는다.

공통 이벤트가 상위 구간의 고정된 시각에 나오면 branch 밖에 둔다. 합류 시각이 달라질 수 있으면 branch 안에 `merge`를 하나 두고 공통 신호와 후속 이벤트를 작성한다. `merge`에는 ID가 없으며 `when`을 하나 이상 둘 수 있다. 각 신호는 OR다. 합류 신호를 상대 시각 0.0의 기준점으로 기록하고 선택을 닫으며 남은 option 이벤트·반복을 취소한다. 선택이 미해결이어도 유일한 공통 신호로 합류할 수 있으며 이전 선택은 `unresolved`로 남는다. 이후 선택 신호는 받지 않는다.

`merge`의 신호는 branch의 `open`부터 상위 구간이 끝날 때까지 감시한다. 각 `when`에 `at=초 before=초 after=초`를 두면 상위 구간 시계의 window를 쓴다. phase 바로 아래 branch에서는 at 생략 시 시간 제한 없이 감시하고, at을 지정하면 before·after의 생략과 경계 규칙은 sync와 같다. 반복 안 branch에서는 모든 merge의 when에 at과 유한한 before·after를 명시해야 한다. 서로 다른 활성 branch의 합류가 같은 관측에 일치하면 ambiguous로 보고하고 합류하지 않는다. 합류는 상위 구간 실행마다 최대 한 번 일어나며 상위 구간 종료 시 닫힌다. 신호 없이 option 완료 시각으로 합류하는 문법은 실제 사례 검증 전까지 두지 않는다.

## 반복

`loop "id" start=초 every=초`는 phase나 선택된 option 안에 둔다. `start`는 그 상위 구간의 상대 시각, `every`는 양의 반복 간격이다. 반복 안 이벤트의 시각은 회차 시작 기준이고 `0.0 <= 시간 < every`여야 한다. 반복 횟수를 지정하지 않으며, 탈출하지 않으면 상위 구간이 끝날 때까지 계속한다.

loop는 시작 전 탈출 감시, 본문 실행, 종료 상태를 구분한다. start 이전에도 유효한 until window를 감시하지만 본문은 실행하지 않는다. start에 도달해 본문을 실행할 때 같은 phase에 이미 본문 실행 중인 다른 loop가 있으면 두 번째 본문을 시작하지 않고 작성 제약 위반을 보고한다. 여러 loop가 정확히 같은 원본 시각에 시작하면 문서 순서대로 시작 여부를 판단한다. 감시만 하는 loop는 이 개수에 포함하지 않는다. 탈출 또는 상위 구간 종료 뒤에는 본문을 재개하지 않는다.

```kdl
loop "hold" start=30.0 every=20.0 {
    until "StartsUsing" id="8EFF" at=30.0 before=15.0
    event "pulse" 5.0 name="Pulse" {
        sync 5.0 "Ability" id="C125" before=2.5 after=2.5
    }
    on-exit {
        event "next" 3.0 name="Next attack"
    }
}
```

`until`은 상위 phase 또는 선택된 option 기준의 `at`에서 `before`부터 `after`까지 감시한다. option에서는 선택 기준점을 더해 phase 시간축으로 계산한다. `at`은 필수, `before` 생략은 0.0초, `after` 생략은 **상위 구간이 끝날 때까지**다. 양 끝을 포함하고 시작이 음수면 0.0부터 감시한다. 같은 window와 동작을 갖는 `until` 신호는 여러 줄로 OR 지정할 수 있다. 예시의 신호는 상위 구간의 상대 시각 15.0초부터 무기한 감시한다. `until`이 없으면 상위 구간이 끝날 때까지 반복한다.

유효한 탈출 신호가 `start`보다 먼저 오면 반복을 실행하지 않고 탈출한다. 탈출 후 미실행 반복 이벤트는 취소하며 loop를 다시 시작하지 않는다. `on-exit`은 선택 사항이며 `until`이 있을 때만 하나 둘 수 있다. 그 안의 이벤트는 탈출 신호 시각을 0.0으로 삼는다. 상위 구간 종료·wipe·구역 이탈로 중단되면 `on-exit`은 실행하지 않는다. 유한 window가 끝나도록 탈출 신호가 없으면 반복을 계속하고 `unresolved`를 보고한다.

`on-exit`의 기준점은 종료된 회차가 아닌 loop 바깥의 phase 시간축에 기록한다. option 안의 loop라면 option과 같은 phase 시간축을 쓴다. 따라서 탈출 후 sync도 phase 시계를 보정하며 종료된 loop를 다시 활성화하지 않는다. 탈출 전이라 아직 회차가 시작되지 않았어도 같은 규칙이다.

반복 안 `sync`가 일치하면 현재 회차의 시작점을 보정하고, **이후 회차도 보정된 시작점에서 `every` 간격으로** 예정한다. 부모 phase 시간축과 `until` window는 이 회차 보정으로 움직이지 않는다. 이미 처리한 회차와 이벤트는 재실행하지 않는다. 같은 관측이 loop 탈출과 반복 이벤트 sync 양쪽에 일치하면 탈출을 우선한다. 서로 다른 loop가 감시 중인 탈출 조건에 한 관측이 일치하면 어느 쪽도 탈출시키지 않고 ambiguous를 보고한다. 상위 구간 종료 시 반복과 on-exit의 후속 이벤트를 취소한다.

반복 안에 branch와 그 `merge`를 둘 수 있다. branch의 선택 window와 `merge` 신호의 window는 각 회차의 시계 기준이고, 회차가 바뀌면 활성 선택과 미실행 이벤트를 닫고 다음 회차의 선택을 새로 시작한다. 각 회차에서의 선택 결과는 이력에 남긴다. `close`는 `every`를 넘을 수 없고, 합류 신호 감시와 후속 이벤트는 해당 회차가 끝나면 취소된다. 취소 동작에 의존해 회차 밖 이벤트를 작성하지 않고 위의 회차 안 완료 제약을 지킨다. 반복의 직접·간접 중첩은 모두 금지한다.

```kdl
loop "rotation" start=30.0 every=20.0 {
    branch "rotation-choice" open=0.0 close=5.0 {
        option "left" {
            when "Ability" id="A001"
            event "left-hit" 3.0 name="Left attack"
        }
        option "right" {
            when "Ability" id="A002"
            event "right-hit" 3.0 name="Right attack"
        }
        merge {
            when "Ability" id="A003" at=10.0 before=1.0 after=1.0
            event "rotation-shared" 2.0 name="Shared attack"
        }
    }
}
```

로그가 짧게 끝났다는 이유만으로 무한 반복이나 주기를 확정하지 않는다. 전투 길이 때문에 별도의 반복 횟수 제한을 두지 않는다.

## 관측과 검토

원본 로그 → 정규화된 발생 후보 → 프로세스 그래프 → 타임라인은 서로 다른 단계다. DFG 간선은 관측된 인접 관계이며 그 자체로 분기 조건이나 전체 실행 경로를 증명하지 않는다.

| 비교 상태      | 의미                                                     |
| -------------- | -------------------------------------------------------- |
| `unobserved`   | wipe 또는 입력 종료로 해당 시점에 도달했는지 알 수 없다. |
| `unobservable` | 필요한 로그 타입이나 필드가 입력에 없다.                 |
| `ambiguous`    | 둘 이상의 대응이나 동작이 가능하다.                      |
| `unresolved`   | 선택 또는 탈출을 결정할 근거가 부족하다.                 |
| `mismatch`     | 관측 가능한 범위에서 모델과 실제 관측이 다르다.          |

사람의 검토 여부는 위 비교 상태와 별개이며 KDL이 아닌 evidence에 둔다. 해시, 보고서·fight, 원본 인덱스와 밀리초 시각, 묶음 근거, 알고리즘·입력 범위, 반올림 차이와 판단도 별도 evidence에 둔다. evidence 형식과 문서 해시 연결은 후속 계약으로 확정한다. 미확정 항목이 있어도 저장·재생을 막지 않고 검증 결과에 요약한다. 전체 항목 확정을 요구하는 엄격 검사는 명시적으로 요청한다.

## 구현 전 검증

- [ ] KDL 예제의 한 줄 신호, 여러 대안과 블록 필드가 같은 내부 조건으로 해석되는지 확인한다.
- [ ] branch의 배치, merge·on-exit의 자식 종류, loop의 직접·간접 중첩, requires의 잘못된 참조·자기 참조·순환 참조를 정적으로 검사하고, 선행 실행 결과의 존재는 재생에서 확인한다.
- [ ] 동시 본문 실행 최대 하나와 회차 안 완료를 실제 사례로 확인한다. 시작 전 탈출 감시는 개수에서 제외하고 두 번째 본문 시작은 위반으로 보고한다. 반복 안 merge의 유한 window와 명확한 범위 초과를 정적으로 검사하며, 관측에 의존하는 조건과 미검사 범위를 별도로 보고한다.
- [ ] 같은 0.1초의 별개 관측, 한 관측의 경쟁 동작, 같은 시각의 신호·예정 이벤트, 유휴 enter, start와 첫 enter, 진입 신호와 0.0 이벤트를 구분해 재생한다. branch의 선택 종료 뒤 보정으로 다시 열리지 않는지 확인하고, 보정으로 반복 경계를 지나는 처리와 여러 제어 동작의 조합을 확정한다.
- [ ] option·merge·on-exit의 기준점과 공유 phase 보정을 검증한다. 같은 시간축의 후속 이벤트·window는 함께 이동하고, 활성 반복의 회차 보정과 부모 보정은 서로 소급 전파되지 않는지 확인한다. 조사한 전투 사례와 독립 로그를 비교한다.
- [ ] 정적으로 증명되는 선택 신호 충돌은 작성 오류로, 실행 중에만 드러나는 충돌은 `ambiguous`로 구분한다.
- [ ] phase 진입 window·이전 phase, fight 기준 이벤트, cross-phase 선택 유지와 wipe 초기화의 계약 및 생성 결과를 검증한다.
- [ ] 선택 신호 누락·중복, 공통 신호에 의한 합류와 미해결 상태를 검증한다. 실제 전투 자료를 비교해 option 완료 기준 합류가 필요한지 확인한다.
- [ ] Valigarmanda의 이전 선택에 따른 후속 경로를 실제 신호와 `requires`로 표현할 수 있는지, 던전의 보스 처치 후 다음 진입에 현재 `from` 규칙이 충분한지 확인한다. 불가능하면 작성 제약으로 감추지 않고 스키마 변경을 검토한다.
- [ ] 반복 시작 전 탈출, window 경계·무기한 감시, 보정된 다음 회차, 선택지별 반복과 상위 구간 종료를 검증한다.
- [ ] 0.1초 반올림·동시 이벤트·충돌, FFLogs 미관측과 ACT 로그 타입 미지원·불일치를 구분한다.
- [ ] 실제 독립 로그와 검증된 전투 자료를 비교하고, 외부 실행기를 사용할 수 있을 때 그 동작도 별도로 확인한다. 번역 리소스와 반복 필드의 구체 문법은 별도 계약으로 정한다.

KDL과 기록된 신호를 받아 상태 전이·예정 이벤트·불일치를 확인하는 오프라인 재생기를 구현한다. 실제 전투에 연결하는 외부 실행기와는 별도이며, 재생 결과만으로 외부 실행기나 실제 게임과의 호환성을 확정하지 않는다. 구현 및 검증 범위는 [재설계 계획](PLAN.md#오프라인-재생-검증)에 정리한다.
