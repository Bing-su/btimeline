# 타임라인 자동생성 구현 계획

작성일: 2026-09-26. 근거는 [연구 결과](timeline-research.md), [SPEC v1](../SPEC.md), 현재 Rust 수집기와 Python 감사 코드다. 이 문서는 구현 제안이며, 생성기·새 명령·검증기는 아직 구현되지 않았다. 연구의 224개 표본 집계는 기존 감사 결과이며 이번 계획 작성에서 재집계하지 않았다.

첫 목표는 **R12S 104·105를 하나의 편집 가능한 YAML 초안으로 생성하고, 원본 로그에 대한 재생 결과를 함께 제공하는 것**이다. 그 다음 cactbot 텍스트 변환, 분기 진입·합류, Dancing Mad 전환, Clyteum 반복 순으로 확장한다.

## 1. 구현 범위와 결정

## 4. CLI와 산출물 계약 제안

아래 명령은 목표 인터페이스 예시이며 현재 CLI에서는 실행되지 않는다. P3은 단일 파일부터, P5는 디렉터리 입력과 전투명 선택까지 지원한다.

```sh
btimeline generate logs/r12s/example_4.json -o out/single-draft.yaml
btimeline generate logs/r12s --name "Lindwurm" -o out/r12s-draft.yaml
btimeline validate out/r12s-draft.yaml
btimeline convert out/r12s-draft.yaml -o out/r12s.txt
```

| 계약          | 동작                                                                                                                                                   |
| ------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 전투 선택     | 전투명에서 실제 입력 그룹을 선택. R12S는 근거 있는 104·105 연결을 지원. 관련 없는 이름·난이도·버전 혼합은 오류 또는 명시적 검토 대상으로 처리          |
| 생성 저장     | `r12s-draft.yaml`과 `r12s-draft.report.json`. 기존 파일을 덮어쓰지 않음. 둘 다 검증·임시 기록 후 저장하고, 여러 파일 전체가 원자적이라고 주장하지 않음 |
| 변환 저장     | 새 `.txt` 파일. 검증 실패 시 출력하지 않음. 기존 출력 덮어쓰기 정책은 기본 거부                                                                        |
| 결정성        | 입력을 고정 순서로 처리하고 동일 시각 source order 유지. 원본 millisecond 유지, YAML 출력 직전에만 반올림                                              |
| 작성자 수정   | 수정 YAML을 validate/convert에 다시 입력. 기존 notes/catalog를 보존. 자동 재생성 병합은 범위 밖                                                        |
| parser 미해결 | Schema·semantic 성공과 parser 미실행을 구분. parser 미검증 결과를 전체 검증 성공으로 표시하지 않음                                                     |

report에는 입력 파일·report/fight/revision/logVersion·수집 완료 상태, occurrence 참조, 역할/능력 매핑, 슬롯별 표본수·시간 통계, observed/unknown 등 조합 근거 상태, 종료 잘림, sync 충돌·비활성 이유, 재생 오류·시간 오차·검증 실행 여부를 기록한다. 입력에 없는 값은 확인된 값처럼 채우지 않는다.

## 5. 검증과 출시 조건

| 검증           | 최소 실행 가능한 확인                                                                                                                           | 통과 기준                                                                                                                 |
| -------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| SPEC 회귀      | 모든 entry를 포함한 정상 fixture와 주요 잘못된 입력을 사용하는 Rust 테스트                                                                      | 결정적 기대 텍스트 일치, 유효하지 않은 입력 거부                                                                          |
| 정규화 회귀    | 동시 helper 둘·timestamp 역전·취소/종료 cast를 가진 작은 fixture                                                                                | 두 실행 및 원본 참조 보존, 가짜 완료 없음                                                                                 |
| 정렬 회귀      | 알려진 대안 조합·선택 이력에 따른 후속·반복 회차·중간 wipe                                                                                      | 순서/개수/의존성 보존. 알려진 선택 슬롯의 미관측 조합은 unknown으로 지원                                                  |
| 재생 회귀      | 반복 ID, 겹치는 window, 전환, 초기화 후 105 진입, B537 시전 중 clear                                                                            | 올바른 signal만 매칭, 종료 이후 미발생을 누락 오류로 세지 않음                                                            |
| 실제 로그 평가 | 중복 pull 후보로 연결된 report를 같은 분할에 둔 holdout, 보조로 중복 후보 묶음 제외 평가. 희귀 후반은 학습/평가의 도달 수와 report 수 별도 공개 | 같은 pull 후보가 학습·평가 양쪽에 없는지 확인. 학습에 없는 경로·늦은 전환을 별도 표시. 표본 부족을 합격으로 해석하지 않음 |
| 기본 확인      | `cargo fmt --check`, `cargo test`, `cargo clippy --all-targets -- -D warnings`                                                                  | 새 변경과 기존 수집기 확인 통과                                                                                           |
| 런타임 호환    | 연구 방침과 parser gate를 해결한 후 cactbot 해석·리셋·표시 검증                                                                                 | 내부 재생만으로 공식 호환성을 주장하지 않음                                                                               |

초안 공개는 P5까지의 SPEC 검증과 근거 보고가 갖춰지면 가능하다. **R12S 사용 가능 판정은 P6의 두 진입 경로 검증이 필수**이며, 공식 호환 판정에는 별도의 parser/runtime gate가 필요하다. 숫자 정확도 기준은 슬롯별 observed window와 holdout 결과로 정하고, 전환 변동을 감추기 위해 일괄 window를 확대하지 않는다.
