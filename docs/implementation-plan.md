# 타임라인 자동생성 구현 계획

P0 산출물: [평가 계약과 검증 체크리스트](evaluation-contract.md), [고정 평가 입력](evaluation-inputs.csv).

작성일: 2026-09-26. 근거는 [연구 결과](timeline-research.md), [SPEC v1](../SPEC.md), 현재 Rust 수집기와 Python 감사 코드다. 이 문서는 단계별 구현 계획이다. P1–P3 단일 파일 생성·검증·변환은 구현되었고 P4 이후는 제안이다. 연구의 224개 표본 집계는 기존 감사 결과이며 이번 계획 작성에서 재집계하지 않았다.

첫 목표는 **지원 형식의 임의 FFLogs 전투 로그에서 편집 가능한 YAML 초안과 원본 재생 결과를 생성하는 것**이다. 단일 로그부터 시작해 동일 전투의 여러 pull, 관측 가능한 분기·전환·반복으로 확장한다. 현재 내려받은 R12S, Dancing Mad, Clyteum 로그는 회귀 사례이며 지원 대상의 목록이 아니다.

## 1. 구현 범위와 결정

| 항목           | 결정                                                                                   | 이유 / 제한                                                                                 |
| -------------- | -------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| 정식 도구      | 기존 Rust CLI에 `generate`, `validate`, `convert`를 추가                               | 수집·인증 경로를 유지하고 Python 의존성을 정식 CLI에 필수화하지 않음                        |
| 정렬 선행 실험 | 기존 Python 감사 코드와 `sequence_align` 후보로 서로 다른 구조의 실제 로그 구간을 비교 | 라이브러리의 실제 로그 적용은 미수행. 일반 DP를 새로 작성하지 않음                          |
| Rust 정렬 도입 | 선행 실험 후 Rust에서 재사용 가능한 구현 하나만 선택                                   | Rust-Bio POA는 후보. 256-symbol 제한과 DAG 특성을 확인하고, 불충족 시 다른 기존 구현을 검토 |
| 모델           | occurrence → anchor 구간 → 위치를 가진 슬롯·경로 → SPEC entries                        | ability ID 하나를 상태 하나로 합치지 않음                                                   |
| 첫 출력        | 공통 구간·검증된 대안 슬롯·유한 반복을 가진 draft YAML + report JSON                   | 판별 불가 분기를 확정 경로처럼 출력하지 않음                                                |
| 의존성         | YAML 1.2와 중복 키 거부를 지원하는 파서, JSON Schema 검증기만 계약상 선행 도입         | 구체 crate와 버전은 도입 시 현재 API·지원 범위를 확인하고 고정                              |
| PM4Py          | 연구용 합성 비교 도구로 유지                                                           | 정식 통합은 모델 발견이 실제로 필요해지고 배포·라이선스 조건을 해결했을 때                  |
| 편집 보존      | 생성은 새 파일에만 수행. 기존 YAML 덮어쓰기 거부                                       | 편집 내용 자동 병합은 별도 기능으로 미룸                                                    |
| 생성 모드      | 기본 `raid`는 전체 구간을 생성하고 `--mode dungeon`은 보스 구간의 적 cast만 생성       | 전투 적 중 `Boss` actor의 첫·마지막 관측 상호작용 사이를 구간으로 잡아 helper 기믹은 유지   |
| SPEC           | v1 필드만 사용                                                                         | graph, confidence, censoring은 report에 기록. SPEC 변경을 전제로 구현하지 않음              |

### 전투 독립 입력 계약

| 경우                  | 처리                                                                                                                |
| --------------------- | ------------------------------------------------------------------------------------------------------------------- |
| 단일 파일             | 전투 이름이나 ID의 사전 목록 없이 report·fight·event 참조와 수집 완료 상태를 검사하고 직선 초안을 생성              |
| 같은 전투의 여러 pull | encounter·difficulty와 버전·actor/ability 호환성을 확인한 뒤 묶음. 충돌하는 입력은 임의로 병합하지 않고 이유를 보고 |
| 서로 다른 encounter   | 기본은 별도 출력. 체크포인트 등 하나의 타임라인 연결은 관측된 진입 신호와 명시적 관계가 있을 때만 허용              |
| 미지 전투·희귀 경로   | 관측 가능한 직선 구간부터 출력. 판별 불가 분기, 부족한 표본, 미지원 신호는 report에 남기고 성공 범위를 제한         |

현재 세 전투의 로그는 위 정책을 검사하는 사례다. 새 전투를 수용하는 데 전투별 ID 조건문이나 이름별 코드 변경이 필요하면 범용 단계의 완료로 보지 않는다.

## 2. 단계별 작업과 완료 기준

작업 단위는 순서대로 병합 가능한 변경이다. P1과 P3의 임의 단일 로그 생성이 첫 수직 구현이며, P4 이후 같은 입력 그룹의 다중 로그 모델로 확장한다. 각 단계는 처음 보는 encounter ID와 전투명에도 같은 정책을 적용한다. P0의 런타임 관련 미결정은 초안 작업을 막지 않지만 호환성 완료 판정을 막는다.

| 단계                        | 구체 작업                                                                                                                                                                                                                                                                                   | 산출물                                                          | 완료 기준 / 다음 단계 조건                                                                                                                                            |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| P0 계약·실험 기준           | 출력 상태를 draft / 내부 검증 통과 / 런타임 호환 검증 완료로 구분. parser 방침 충돌, sync 선택 순서·window 경계·동시 exit/forcejump·리셋·lookahead를 미검증 항목으로 기록. 서로 다른 report의 중복 pull 후보를 같은 평가 묶음에 두고 분할을 고정. 현재 로그 회귀와 새 전투 평가 절차를 구분 | 평가 입력 목록과 검증 체크리스트                                | 각 주장에 사용한 검증 방법이 연결됨. 고정 목록은 무결성·후보 묶음을 검사하며 기존 세 전투만으로 범용성을 주장하지 않음. 공식 타임라인·트리거를 정답으로 사용하지 않음 |
| P1 SPEC 기반                | YAML 로드 → JSON Schema → semantic 검증 → 결정적 렌더러. 모든 entry variant와 notes/catalog 순서 구현                                                                                                                                                                                       | `schema/btimeline-v1.schema.json`, `validate`, `convert`의 핵심 | SPEC fixture를 텍스트와 정확 비교. 중복 키·다중 문서·미지 키·잘못된 jump·regex·시간 정밀도·순서 위반 거부. parser gate 미해결 상태를 성공으로 숨기지 않음             |
| P2 입력·정규화              | 기존 감사 항목을 생성 입력 검사에 반영. encounter·difficulty·버전·actor/ability 호환성으로 입력 그룹을 판별하고 timestamp 안정 정렬, 역할·instance, 시작/완료, 동시묶음, 종료 상태 보존                                                                                                     | 그룹 판정과 원본 참조를 가진 occurrence                         | 새 전투명·ID에도 동일 검사. 혼합 입력은 오류 또는 검토 대상으로 보고. 파일·이벤트 index로 역추적하고 불완전 수집을 거부. 종료로 사라진 완료는 미관측 처리             |
| P3 단일 로그 수직 구현      | 완료 cast를 `Ability` 행으로 생성. 이름 regex escape, 능력 목록·provenance note 생성. 제외 이벤트까지 sync 충돌 검사                                                                                                                                                                        | 단일 로그 `draft.yaml`, `report.json`, `report.md`              | 실제 완료 시각을 사용하고 최종 단계에서만 0.1초 반올림. 동일 입력의 YAML이 바이트 단위로 동일. 충돌 sync는 비활성화하고 이유 표시                                     |
| P4 다중 로그 정렬 실험·통합 | 같은 그룹의 boss anchor와 helper 시작/완료·instance·개수로 구간 정렬. 후보 라이브러리로 입력 순서와 반복 오대응 평가 후 Rust 연결                                                                                                                                                           | 슬롯·구간·대응 근거, 선택한 정렬 구현                           | 합성 대안·반복과 실제 서로 다른 전투 그룹에서 순서·후속 의존성 보존. wipe 접미부는 미관측. 병합 순서에 따라 경로가 바뀌면 보고                                        |
| P5 다중 로그 초안           | 그룹별 블록 진입 기준 중앙값·min/max·표본수 산출. 동일 후속의 대안만 ID 배열로 병합하고 근거 없는 반복은 유한하게 펼침                                                                                                                                                                      | 입력 그룹별 YAML + 생성 report                                  | 하나의 encounter를 입력하면 그 그룹만으로 생성. 연속 encounter 연결은 별도 관측 근거가 있을 때만 적용. 판별 불가 분기는 공통 초안과 제한을 보고                       |
| P6 재생·진입 검증           | 관측 신호를 가상 시계에 재생하고 활성 sync, 반복 ID, kill/wipe 종료, 분기 진입·합류, 초기화 후 독립 진입을 검사                                                                                                                                                                             | 파일·행별 재생 결과와 holdout 평가                              | 입력 그룹마다 오매칭·잘못된 jump·관측 의존성 위반 0. 종료 잘림과 누락을 구별하고 시간 오차·window 미검출을 별도 집계                                                  |
| P7 분기·페이즈 확장         | 판별 신호가 있는 경로를 label/sync jump로 컴파일. 입력별 관측 신호와 보정된 가상 시계로 전환 window 산정                                                                                                                                                                                    | 분기 블록과 전환 초안                                           | 서로 다른 전투의 전환 사례와 합성 미지 경로에서 오활성 sync 0. lookahead 표시와 실제 진입을 각각 검증. 미검증 우선순위에 의존하는 forcejump 제한                      |
| P8 반복 압축                | 역할·instance·targetability 등 관측 문맥으로 회차·출구 대응. 충분한 wipe·clear 근거가 있을 때만 반복 압축                                                                                                                                                                                   | 조건부 반복 후보와 근거 report                                  | 서로 다른 전투의 반복 사례와 합성 출구 부재 사례에서 회차·간격·출구를 재생으로 설명. 근거 부족 시 유한 행 유지                                                        |

P3의 `--mode`는 `raid`와 `dungeon`을 받으며 기본값은 `raid`다. `raid`는 전체 구간을 생성하고, `dungeon`은 해당 전투의 적 `Boss` actor별 첫·마지막 상호작용 구간만 YAML 행과 ability catalog에 반영한다. 보스 구간 밖의 occurrence는 근거 보고서에 보존한다. report에는 모드와 관계없이 actor별 관측 시작·종료 시각을 기록하며, `dungeon`에서 보스가 관측되지 않으면 오류로 처리한다. 구간 경계는 관측 기반 초안이므로 전투별 첫 진입 시각과 보스 간 이동 시간은 그대로 남는다. P4–P6에서 보스별 진입 sync·시계 재설정·구간별 재생을 검증한 뒤 런타임 동기화 완료로 판정한다.

P3의 표시 행은 원본 밀리초 시각·actor ID·ability ID가 같은 완료 cast에서 첫 이벤트 하나만 남긴다. instance별 실행은 `report.json`의 `occurrences`와 `collapsedCasts`에 보존한다. sync 충돌은 출력에서 생략한 cast를 포함한 전체 원본으로 검사하며, 서로 다른 시각의 cast는 기본 sync window가 겹쳐도 합치지 않는다. 이 정책은 별도 on/off 플래그 없이 적용한다.

## 4. CLI와 산출물 계약 제안

아래 단일 파일 명령은 현재 CLI에서 실행된다. 디렉터리 입력과 `--name` 선택은 P5 목표다. P3은 단일 파일부터, P5는 디렉터리 입력의 자동 그룹 선택까지 지원한다. 여러 호환 그룹이 있으면 선택을 요구하며 전투명은 표시·선택용이다.

```sh
btimeline generate logs/example/fight_4.json -o out/single-draft.yaml
btimeline generate logs/example/fight_4.json --mode dungeon -o out/dungeon-draft.yaml
btimeline generate logs/example --name "Example Fight" -o out/fight-draft.yaml
btimeline validate out/fight-draft.yaml
btimeline convert out/fight-draft.yaml -o out/fight.txt
```

생성되는 `draft.yaml`의 첫 줄은 `# yaml-language-server: $schema=https://raw.githubusercontent.com/Bing-su/btimeline/main/schema/btimeline-v1.schema.json`로 고정한다. 편집기에서 이 저장소의 공개 v1 스키마를 참조하도록 하기 위한 지시문이다.

| 계약          | 동작                                                                                                                                                                               |
| ------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 전투 선택     | 입력에서 호환 그룹을 발견하고 둘 이상이면 명시적 선택을 요구. 이름은 표시·선택용이며 ID/이름 하드코딩 없이 처리. 연속 전투 연결은 별도 근거가 있을 때만 허용                       |
| 생성 저장     | 지정한 `fight-draft.yaml`과 짝이 되는 `.report.json`과 검토용 `.report.md`. 기존 파일을 덮어쓰지 않음. 모두 검증·임시 기록 후 저장하고 여러 파일 전체가 원자적이라고 주장하지 않음 |
| 변환 저장     | 새 `.txt` 파일. 검증 실패 시 출력하지 않음. 기존 출력 덮어쓰기 정책은 기본 거부                                                                                                    |
| 생성 모드     | 기본 `raid`는 전체 구간 출력. `--mode dungeon`은 보스 구간만 생성. report에 모드·actor별 관측 시작/종료 시각 기록                                                                  |
| 결정성        | 입력을 고정 순서로 처리하고 동일 시각 source order 유지. 원본 millisecond 유지, YAML 출력 직전에만 반올림                                                                          |
| 작성자 수정   | 수정 YAML을 validate/convert에 다시 입력. 기존 notes/catalog를 보존. 자동 재생성 병합은 범위 밖                                                                                    |
| parser 미해결 | Schema·semantic 성공과 parser 미실행을 구분. parser 미검증 결과를 전체 검증 성공으로 표시하지 않음                                                                                 |

report에는 입력 파일·report/fight/revision/logVersion·수집 완료 상태, occurrence 참조, 역할/능력 매핑, 슬롯별 표본수·시간 통계, observed/unknown 등 조합 근거 상태, 종료 잘림, sync 충돌·비활성 이유, 재생 오류·시간 오차·검증 실행 여부를 기록한다. 입력에 없는 값은 확인된 값처럼 채우지 않는다.

## 5. 검증과 출시 조건

| 검증           | 최소 실행 가능한 확인                                                                                                                           | 통과 기준                                                                                                                                  |
| -------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| SPEC 회귀      | 모든 entry를 포함한 정상 fixture와 주요 잘못된 입력을 사용하는 Rust 테스트                                                                      | 결정적 기대 텍스트 일치, 유효하지 않은 입력 거부                                                                                           |
| 보스 구간 회귀 | 보스 전·사이·후 잡몹과 보스전 helper를 가진 합성 로그, 실제 Clyteum 입력                                                                        | `raid`/`dungeon` 출력 차이와 구간 근거 확인. 보스전 helper 유지, 잡몹 행 제외, 보스 미관측 오류                                            |
| 정규화 회귀    | 동시 helper 둘·timestamp 역전·취소/종료 cast를 가진 작은 fixture                                                                                | 두 실행 및 원본 참조 보존, 가짜 완료 없음                                                                                                  |
| 정렬 회귀      | 알려진 대안 조합·선택 이력에 따른 후속·반복 회차·중간 wipe                                                                                      | 순서/개수/의존성 보존. 알려진 선택 슬롯의 미관측 조합은 unknown으로 지원                                                                   |
| 재생 회귀      | 반복 ID, 겹치는 window, 전환, 초기화 후 독립 진입, 시전 중 clear의 합성 및 실제 사례                                                            | 올바른 signal만 매칭, 종료 이후 미발생을 누락 오류로 세지 않음                                                                             |
| 신규 전투 수용 | 기존 세 전투에 없는 이름·encounter ID와 능력 ID를 가진 합성 fixture, 이후 확보한 새 전투 로그를 같은 CLI에 입력                                 | 코드 수정 없이 단일 초안·그룹 판정·재생 결과 생성. 새 실제 로그의 holdout은 별도 고정하고, 확보 전에는 범용 실전 검증 완료를 주장하지 않음 |
| 실제 로그 평가 | 중복 pull 후보로 연결된 report를 같은 분할에 둔 holdout, 보조로 중복 후보 묶음 제외 평가. 희귀 후반은 학습/평가의 도달 수와 report 수 별도 공개 | 같은 pull 후보가 학습·평가 양쪽에 없는지 확인. 학습에 없는 경로·늦은 전환을 별도 표시. 표본 부족을 합격으로 해석하지 않음                  |
| 기본 확인      | `cargo fmt --check`, `cargo test`, `cargo clippy --all-targets -- -D warnings`                                                                  | 새 변경과 기존 수집기 확인 통과                                                                                                            |
| 런타임 호환    | 연구 방침과 parser gate를 해결한 후 cactbot 해석·리셋·표시 검증                                                                                 | 내부 재생만으로 공식 호환성을 주장하지 않음                                                                                                |

초안 공개는 P5까지의 SPEC 검증과 근거 보고가 갖춰지면 가능하다. **범용 지원 주장은 P6에서 처음 보는 전투명·encounter ID의 입력을 코드 수정 없이 생성·재생하고, 적용 가능한 기능의 오류와 미지원 범위를 구분한 뒤에만 가능**하다. R12S의 두 진입 경로는 그중 별도 사례 검증이다. 공식 호환 판정에는 parser/runtime gate가 필요하다. 숫자 정확도 기준은 슬롯별 observed window와 holdout 결과로 정하고, 전환 변동을 감추기 위해 일괄 window를 확대하지 않는다.

## 6. 사례별 미결정 사항과 필요한 추가 입력

| 항목                                    | 현재 계획                                                         | 필요한 근거 / 영향                                                                             |
| --------------------------------------- | ----------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| 공식 검증 코드 제외 vs SPEC parser gate | 초안·독립 재생을 먼저 구현. SPEC나 연구 방침은 자동 변경하지 않음 | 검증 목적으로 공식 parser 사용을 허용할지, 계약을 별도로 수정할지 결정해야 최종 호환 판정 가능 |
| 104 종료→105 진입                       | 본문 생성과 독립 105 anchor 분석은 진행                           | 인접 fight 사이 All events 필요. 91–114초 준비 간격을 전환 시간으로 복사하지 않음              |
| B528 진입 신호                          | 초기화된 시계의 window·source·문맥을 우선 검증                    | 반복 B528과 구별되지 않으면 하나의 파일에 두 진입 지원은 미완료로 표시                         |
| B537 종료·후속                          | 두 B533 회차와 관측 B537을 펼쳐 보존                              | 추가 긴 pull과 실제 신호로 종료 조건·충돌·후속 유무 확인                                       |
| Dancing Mad 전환                        | 기존 후반 wipe 8개부터 분석                                       | `phaseTransitions`를 실제 cast/targetability 신호에 대응. 14.689초 변동은 관측 범위로만 사용   |
| Clyteum 반복 출구                       | 무한 loop를 생성하지 않음                                         | 전환 직전·후반 wipe 추가 수집 후 exit 우선순위와 회차 검증                                     |

착수 순서는 **P0 계약 정리 → P1 검증·변환 기반 → P2/P3 임의 단일 로그 초안 → P4/P5 동일 그룹 다중 로그 → P6 새 전투 재생 검증 → P7/P8 확장**이다. 기간 추정은 P3 수직 구현과 P4 실제 정렬 실험 후 산정한다. UI, 데이터베이스, 범용 process miner, 무한 반복 추론, 편집 자동 병합은 첫 구현에 포함하지 않는다.
