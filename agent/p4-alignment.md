# P4 다중 로그 정렬 결과

## 사용

```sh
btimeline align logs/clyteum/AVxmgdNytFPBwLRH_31.json logs/clyteum/BTxgcVRnWMpDrK9X_30.json > alignment.json
```

`align`은 P2의 입력 검사로 호환되는 한 그룹만 받아 모든 pull 쌍을 비교한다. 입력 순서를 바꿔도 report/fight/file 순으로 정렬하므로 출력이 같다. YAML 분기 생성은 P7의 작업이다.

| 단계 | 정렬 근거                                                                                                                                                                          |
| ---- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 신호 | actor game ID·역할, ability ID, 시작/완료 종류, 동시 발생 개수·고유 instance 개수. 원본 event index와 instance ID 보존                                                             |
| 앵커 | 적 Boss의 완료 cast를 먼저 맞춤. 같은 능력의 반복 앵커는 회차를 별도 위치로 유지하고 `repeatCandidate`로 표시                                                                      |
| 구간 | 대응된 보스 앵커 사이의 모든 신호를 [similar 3 Myers/LCS](https://docs.rs/similar/latest/similar/fn.capture_diff_slices.html)로 정렬. 보스가 대응되지 않으면 그 신호도 구간에 남김 |
| 경로 | 각 구간의 두 pull 경로와 공통 후속 앵커를 함께 보존. `divergentObservedPaths`는 관측 차이이며 분기 조건이 검증됐다는 뜻은 아님                                                     |
| 종료 | wipe 종료 후의 반대편 신호는 `*UnobservedAfterWipe`로 표기. 종료 전 차이는 관측 경로 차이로 유지                                                                                   |
| 순서 | 좌우를 바꿔 재정렬한 대응이 다르면 `orderSensitive: true`로 보고                                                                                                                   |

## 실제 로그 점검

다음은 고정 평가 입력의 각 그룹에서 두 파일만 고른 정렬 실험이다. 개수는 정렬 진단값이며 전투 모델의 정확도 점수가 아니다.

| 그룹 · 입력 fight                                       | 공통 보스 앵커 | 반복 앵커 키 | 다른 관측 경로 구간 | wipe 잘림 구간 | 방향 민감 |
| ------------------------------------------------------- | -------------: | -----------: | ------------------: | -------------: | --------- |
| Clyteum · `AVxmgdNytFPBwLRH_31` / `BTxgcVRnWMpDrK9X_30` |             50 |           18 |                  41 |              0 | 아니오    |
| Dancing Mad · `4cnjwGdZq9PbKVMN_1` / `_2`               |              2 |            0 |                   0 |              1 | 아니오    |
| R12S · `4kz6WLqPGAJ2p8xg_1` / `_10`                     |             33 |            9 |                  17 |              0 | 예        |

세 Clyteum pull의 모든 세 쌍을 출력하고 CLI 입력 순서를 역전한 JSON이 바이트 단위로 같음을 확인했다. 합성 테스트는 대안 시작/완료 순서와 공통 후속, 반복 회차, wipe 접미부, 교차된 동시 instance를 검사한다. wipe 접미부 사후조건은 `contracts`가 항상 검사하고 신호·정렬 개수 조건은 debug 빌드에서 검사한다. cast 시작점의 마지막 일치 항목 선택과 나머지 목록 보존은 `cargo test generate::pairing::tests`의 경계값·속성 테스트로 검사한다. 로그 입력 테스트는 취소, instance 분리, 중복 완료, 같은 시각의 원본 순서를 검사한다.

## 다음 단계에 전달하는 한계

| 상태                           | 처리                                                                                  |
| ------------------------------ | ------------------------------------------------------------------------------------- |
| 같은 보스 능력이 반복됨        | 위치는 보존하지만 회차 대응은 후보로 둔다. 다른 후속 흐름을 섣불리 합치지 않는다.     |
| 정렬 방향에 따라 대응이 달라짐 | 해당 비교의 `orderSensitive`를 기록한다. R12S 사례는 검토 대상이다.                   |
| 다른 관측 경로                 | 구간별 양쪽 경로를 보존한다. 진입 신호가 검증되기 전에는 YAML 분기로 확정하지 않는다. |
| 여러 pull의 전체 모델          | 모든 쌍의 근거를 제공한다. 공통 슬롯의 전역 합의와 YAML 생성은 P5 이후 작업이다.      |
